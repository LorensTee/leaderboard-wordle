### Phase 3 implementation deviations (2026-08-30 — recorded per the implementation prompt §3 rule)

| Deviation | What was done and why |

| **Calendar-adaptive integration fixtures** | The day frames are anchored to the real DB clock (`transaction_timestamp()` Manila), so a test cannot fabricate "today". On frame-poor calendar days (e.g. Mon–Wed in a week, or the 1st–7th of a month) the PROVISIONAL thresholds (3/8) cannot be reached by ANY fixture — the week/month boards are then necessarily empty. The suites compute frame capability in SQL and assert the deepest semantics the calendar allows, ALWAYS asserting the scored-level facts (completedDays, the documented empty-board rule) — never a silent skip. Full aggregation math (frozen MISSED penalty inside a qualified player's average, ranking determinism, tiebreaker day set) asserts on the ~25+ days/month where the frame can host the threshold. |
| **Tiebreaker-day-set test uses constructed raw timestamps (I13)** | `completed_at` is a raw game fact; the fixture may set any value. In REAL wall-clock terms a today-dated completion is always later than past-day completions, so "today's participation" would never change `MIN(completed_at)` — the domain rule (the MIN covers the same day set as the average, D5) is therefore validated with constructed instants (today-dated game @09:00Z vs past-day completions @10:00Z/@12:00Z). | **CI failure #1 (fixed 2026-08-30, `929ec44`)** | The first GitHub Actions `unit-and-build` run failed in `bun run build`: vite 8.2.2 fires `closeBundle` once per build environment, and the CLIENT phase runs before `@sveltejs/adapter-cloudflare` writes `.svelte-kit/cloudflare/_worker.js`. | **CI failure #2 (fixed 2026-08-30, I5c rewrite)** | The `integration` job failed on I5c ("expected 0 to be greater than or equal to 1"): the test asserted at least one finalization from two concurrent sweeps racing an expired-puzzle guess. That interleaving is genuinely nondeterministic — the guess holds the puzzle row lock (`FOR UPDATE`) during its short rejection round-trip, and `FOR UPDATE SKIP LOCKED` then makes BOTH sweeps legitimately skip the row (skip-locked by design: the guess won the serialization point). The product guarantees are different and now asserted deterministically: (1) a sentinel-held lock pins that a sweep skips locked rows (returns `[]`); (2) the guess can never succeed and writes nothing (NG9 discipline); (3) at most ONE real finalization across two concurrent sweeps (finalizePuzzle serializes; SKIP LOCKED + idempotency cover the rest); (4) a raced-away sweep never loses the day — the NEXT sweep finalizes the row (self-healing reconciliation, the plan's documented lazy/missed-cron recovery). | **CI failure #3 (fixed 2026-08-30, batched month fixtures + timeout headroom)** | The `integration` job timed I9 out at 30s. Root cause: I9/I11/I12 seed `dayOfMonth − 1` (up to 30) finalized days, each via its own answer + puzzle insert + per-day game inserts — ~60+ Neon round trips whose cost scales with the calendar day. | **Audit A — sweep `FOR UPDATE SKIP LOCKED` scope (resolved 2026-08-30, no mechanism change)** | The Phase-3 correctness audit flagged that `finalizeExpired()`'s `SELECT … FOR UPDATE SKIP LOCKED` runs through `db.execute()` in autocommit (the statement's row lock ends with the SELECT), while the real finalization happens per row in `finalizePuzzle()`'s own transaction re-acquiring the puzzle lock. Evaluation result: the mechanism exactly matches the plan's authoritative contract (plan §6: sweep-level SKIP LOCKED selection + per-row `finalizePuzzle` "idempotent, own transaction" whose already-FINALIZED re-entry "covers the rest"). Correctness holds in EVERY interleaving — two concurrent sweeps may both select a row, but finalizePuzzle re-locks puzzle-first (NG9) and at most ONE real finalization happens (losers observe FINALIZED via READ COMMITTED post-lock re-read → write-free `alreadyFinalized`); rows skipped because another transaction held their lock self-heal on the next sweep/lazy read. Holding the sweep's SELECT locks across finalization was evaluated and REJECTED: per-row own-transaction finalizePuzzle with a pooled driver runs on a different connection than the held lock → deadlock (the plan's structure is the correct one). Action taken: the code comments now state the precise semantics (SKIP LOCKED = soft selection filter; idempotent finalizePuzzle = the authoritative guard), and a dedicated integration test **I5d** pins the guarantee directly (two concurrent sweeps → ≤1 real finalization, exactly one frozen average/penalty set, FORFEITED conversion, raw facts untouched; run 5× on live Neon). |
| **Audit B — swallowed cron failures (resolved 2026-08-30, changed)** | The audit flagged that `scheduled()` caught + logged `runSettlement()` failures without rethrowing, so a failed settlement looked successful to the platform (invocation resolves OK). Resolution: the handler now rethrows after the structured log, so the cron invocation is marked FAILED in the Cloudflare dashboard. This is a recorded deviation from the plan §7.3 literal wording ("errors are caught and logged") — the plan's own parenthetical ("a thrown error still marks the run failed in the dashboard") is the operative intent, and the repo's fail-closed + structured-marker philosophy favors surfacing. Rethrowing adds no risk: cron deliveries are at-most-once (no auto-retry duplication) and `runSettlement` is retry-safe by construction (SKIP LOCKED selection + idempotent finalizePuzzle/activateToday + self-healing lazy reconciliation), so a re-invocation or the next run is always harmless.
